# Start with a small win

You already write software. This book helps you turn that experience into the ability to build,
evaluate and operate AI systems. Start with a working baseline and keep asking what the evidence
supports.

## Check your starting point

Try these without an assistant generating the first attempt. Documentation is welcome. This is a
diagnostic, not a timed entrance exam.

1. Read a CSV with Python, count missing values, and write a function with one meaningful test.
2. Make a Git commit and explain what is included and excluded.
3. Call an HTTP endpoint, inspect a failed response, and avoid committing a credential.
4. Explain the difference between a percentage and a percentage-point change: from 20% to 25%
   is 5 percentage points and a 25% relative increase.
5. Explain why `(100, 1) + (100,)` can create an unexpected array. If this is unfamiliar,
   Chapter 2 is the right place to learn it.

If the first three are new, use the programming resources in
[Chapter 1](../01-getting-oriented/README.md). If only the numerical work is unfamiliar, begin the
normal path. You do not need to complete a mathematics textbook before writing your first baseline.

## Your next useful hour

Create a repository and a learning log. Write one sentence naming a person, a decision and the data
that might help: “A support lead wants to identify tickets needing escalation, using information
available when the ticket arrives.” Then follow
[orientation week](../01-getting-oriented/README.md#your-week-0-plan).

Choose one role to investigate, while retaining the shared foundations. The role branches in
[Chapter 7](../07-specialisation/README.md) explain what to implement, what to explain and what to
recognize. You are not required to complete every branch.

## The book has three reading layers

**Core.** Follow the chapter plan, work through its example, and attempt the exercise before opening
the answer. Each chapter ends with evidence you can demonstrate.

**Practice.** Diagnose a failure, compare alternatives, and document the limits of a result. Build on
the same project where the domain and data make sense.

**Research.** Optional notes and annotated resources provide depth. A recent paper is a candidate to
understand and test; its publication date does not make it a default production choice.

Reading time shown on the website estimates reading only. Practice-hour figures are planning
allowances for someone who already develops software. They are not measured completion times.

## Two ways to work on the same path

The [reference laboratory](../labs/README.md) gives you synthetic data, reproducible commands,
filled evidence reports and deliberate failures. Run it locally with Python. Its observations are
illustrations of specified assumptions, not evidence of real commercial impact.

Your **independent project** uses data you sourced and are permitted to use. Apply the Chapter 2
dataset checklist. Freeze the holdout when the supervised question is chosen, before outcome-informed
exploration or learned preprocessing. If the dataset cannot support the next claim, narrow the claim
or collect suitable data; the reference lab is available for practice.

## A useful completion standard

You can run the work from a clean checkout, explain one consequential decision, diagnose a plausible
failure, and show a result with its limitations. Documentation can stay open. A negative or
inconclusive comparison is a completed analysis when it is honest and reproducible.

## Read offline

The website includes a complete print edition and an EPUB download. Interactive figures have static
explanations, and the Python laboratory runs without a model API. Browser reading progress is stored
on your device and can be cleared from the reader controls. It does not synchronize across devices.
